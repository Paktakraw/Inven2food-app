# Inven2Food — System Design & Tech Stack

วันที่: 2026-11-27 · สถานะ: ผู้ใช้อนุมัติแล้ว · เอกสารคู่กับ `2026-11-27-inven2food-design.md` (ที่อธิบายว่า "ทำอะไร") ฉบับนี้อธิบายว่า "สร้างอย่างไร"

> ทุกข้อในเอกสารนี้เป็น **[การตัดสินใจของผู้ออกแบบ]** ยกเว้น Supabase ที่ผู้ใช้เลือกเอง ผู้ใช้ยังไม่ได้อนุมัติ แก้ได้ทุกข้อ
> ขอบเขตล่าสุด: ระบบจัดการวัตถุดิบภายในเท่านั้น ไม่มีรายการสั่งจากลูกค้าหรือการขาย

## 1. ภาพรวมสถาปัตยกรรม

```
 มือถือ / คอมพิวเตอร์ (เบราว์เซอร์)
        │  HTTPS
        ▼
 ┌───────────────────────┐        ┌────────────────────────────────┐
 │  Next.js (Vercel)     │  JS    │ Supabase                       │
 │  - หน้าเว็บ (React)    │ client │  - Auth (ผู้ใช้คนเดียว)          │
 │  - อ่านข้อมูล/แสดงผล   │───────▶│  - Postgres                    │
 │  - ฉบับร่าง checklist  │        │     ตาราง + view + RLS          │
 │    (localStorage)     │        │     ฟังก์ชัน SQL (RPC) ที่ทำ     │
 └───────────────────────┘        │     งานตัดของ/นำเข้าคลัง/ยกเลิก  │
                                  └────────────────────────────────┘
```

หลักคิดสำคัญ: **กฎธุรกิจที่แก้ยอดของคงเหลือ (ตัดตามหลักใช้ของที่หมดอายุก่อน, นำเข้าคลัง, ยกเลิก, ปรับยอด) อยู่ในฟังก์ชัน SQL ในฐานข้อมูล ไม่ใช่ในโค้ดหน้าเว็บ** เหตุผล:
- ไลบรารี `supabase-js` ทำหลายคำสั่งใน transaction เดียวไม่ได้ แต่ฟังก์ชัน SQL ทำได้ ทำให้การตัดจากหลายรอบที่ซื้อสำเร็จทั้งหมดหรือไม่สำเร็จเลย ไม่มียอดค้างครึ่งทาง
- ใช้ `SELECT ... FOR UPDATE` ล็อกรอบที่ซื้อที่เกี่ยวข้อง กันยอดเพี้ยนถ้ากดซ้ำหรือเปิดสองหน้าจอ
- ตัวเลขของคงเหลือคือความน่าเชื่อถือของทั้งระบบ จึงควรมีทางเข้าแก้ไขเพียงทางเดียวและทดสอบได้

## 2. Tech Stack

| ชั้น | เลือก | เหตุผลสั้น ๆ |
|---|---|---|
| ฐานข้อมูล + Auth | **Supabase** (Postgres, Supabase Auth) | ผู้ใช้เลือก ได้ Postgres จริง มี transaction, view, ฟังก์ชัน |
| หน้าเว็บ | **Next.js (App Router) + TypeScript** | เว็บเดียวใช้ได้ทั้งมือถือและคอม |
| สไตล์/คอมโพเนนต์ | **Tailwind CSS + shadcn/ui** | ทำหน้าจอใช้งานบนมือถือได้เร็ว ปุ่มใหญ่ ฟอร์มชัด |
| การดึงข้อมูลฝั่งหน้าเว็บ | **supabase-js** (+ TanStack Query ถ้าต้องการแคช) | ใช้ client ตรงกับ Supabase ไม่ต้องมีเซิร์ฟเวอร์ API แยก |
| ฟอร์ม/ตรวจข้อมูล | **React Hook Form + Zod** | ฟอร์มนำเข้าคลังและสูตรมีหลายช่อง ต้องตรวจก่อนส่ง |
| ทดสอบตรรกะฐานข้อมูล | **pgTAP** ผ่าน Supabase CLI (`supabase test db`) | ทดสอบฟังก์ชันตัดของ/แปลงหน่วยกับ Postgres จริง |
| ทดสอบหน้าเว็บ | **Vitest** (ฟังก์ชันช่วยเหลือ เช่นจัดรูปแบบวันที่) + **Playwright** (เส้นทางหลักไม่กี่เส้น) | ครอบเฉพาะที่คุ้ม |
| โฮสต์เว็บ | **Vercel** | ใช้กับ Next.js ง่ายที่สุด มีแผนฟรีพอสำหรับผู้ใช้คนเดียว |
| เวอร์ชันฐานข้อมูล | **Supabase migrations** (ไฟล์ SQL ใน repo) | สคีมาและฟังก์ชันตรวจย้อนหลังและสร้างใหม่ได้ |

ไม่ได้ล็อกเวอร์ชันไลบรารีในเอกสารนี้ ให้ผู้สร้างใช้เวอร์ชันเสถียรล่าสุด ณ ตอนเริ่ม

**ทางที่พิจารณาแล้วไม่เลือก**
- *เขียนเซิร์ฟเวอร์ API แยก (Express/NestJS):* เพิ่มส่วนที่ต้องดูแลโดยไม่จำเป็น เพราะผู้ใช้คนเดียวและกฎสำคัญอยู่ในฐานข้อมูลอยู่แล้ว
- *ตัดของในโค้ด TypeScript ฝั่งหน้าเว็บ:* ไม่มี transaction ข้ามหลายคำสั่ง เสี่ยงยอดเพี้ยน
- *แอปมือถือเนทีฟ:* ต้นทุนสูง เว็บที่ปรับให้เหมาะกับมือถือเพียงพอสำหรับงานนี้

## 3. โมเดลข้อมูล

ทุกตารางมีคอลัมน์ `owner_id` (เท่ากับ `auth.uid()`), `created_at`, `updated_at` ปริมาณใช้ `numeric(14,4)` เงินและต้นทุนต่อหน่วยฐานใช้ `numeric(18,8)` (ไม่ปัดเศษ)

| ตาราง | หน้าที่ | คอลัมน์สำคัญ |
|---|---|---|
| `ingredients` | วัตถุดิบ | ชื่อ, `base_unit` (กรัม/มิลลิลิตร/ชิ้น), `default_zone`, `reorder_point`, `expiry_warn_days` (ค่าเริ่มต้น 3), `default_shelf_life_days` (ถ้ามี) |
| `purchase_units` | หน่วยที่ซื้อ → หน่วยฐาน | `ingredient_id`, ชื่อหน่วย (กก., ถาด, ขวด), `factor` (กี่หน่วยฐานต่อ 1 หน่วยซื้อ) |
| `lots` | รอบที่ซื้อ | `ingredient_id`, `qty_remaining`, `unit_cost`, `purchased_on`, `expires_on` (null ได้), `zone` |
| `stock_movements` | บัญชีแยกประเภทการเคลื่อนไหว (ห้ามแก้/ลบ) | `lot_id`, `qty_delta` (+/−), `reason` (`opening`, `purchase`, `cook`, `cook_reversal`, `count_adjust`, `waste`), `cooking_log_id` (ถ้ามี), `unit_cost` ณ ตอนนั้น |
| `menus` | รายการอาหาร | ชื่อ, `archived` |
| `recipe_items` | สูตรต่อ 1 จาน | `menu_id`, `ingredient_id`, `qty` (หน่วยฐาน), `yield_pct` (ค่าเริ่มต้น 100) |
| `cooking_logs` | บันทึกการทำ (หนึ่งแถวต่อหนึ่งครั้งที่กดบันทึกการทำ) | `menu_id`, `qty` (จำนวนจาน), `note` (ข้อความอิสระ ไม่บังคับ), `status` (`done`, `cancelled`), `total_cost` (คำนวณตอนบันทึก), `made_at` |
| `shopping_items` | รายการซื้อ | `ingredient_id` (หรือชื่ออิสระ), `planned_qty`, `source` (`manual`/`low_stock`/`planned_menu`), `status` (`planned`/`checked_in`), ข้อมูลที่กรอกตอนซื้อ (ราคารวม, ปริมาณ, หน่วย, วันหมดอายุ) |

**หลักการ**
- ไม่มีตารางรายการสั่ง ลูกค้า หรือการขาย ตามขอบเขตที่ผู้ใช้กำหนด
- `lots.qty_remaining` ต้องเท่ากับผลรวม `qty_delta` ของรอบนั้นเสมอ (ตรวจด้วยการทดสอบ) รอบที่ซื้อห้ามลบถ้ามีรายการเคลื่อนไหวอ้างถึง เก็บเป็นยอด 0
- ตารางใช้ `ON DELETE RESTRICT` กับสิ่งที่มีประวัติ ใช้ `archived` แทนการลบวัตถุดิบ/รายการอาหารที่เคยถูกใช้
- `cooking_logs` ไม่มีสถานะรอทำ บันทึกแล้วตัดของทันที สถานะมีเพียง `done` กับ `cancelled`

**View ที่คำนวณให้ (ไม่เก็บซ้ำ)**
- `ingredient_stock`: ยอดคงเหลือต่อวัตถุดิบ = ผลรวมรอบที่ซื้อที่ไม่หมดอายุ (`expires_on` เป็น null หรือ ≥ วันนี้ตามเวลา Asia/Bangkok)
- `menu_availability`: จำนวนจานที่ทำได้ = ค่าต่ำสุดของ `ingredient_stock.qty ÷ (recipe qty ÷ yield)` ในทุกวัตถุดิบของสูตร, และรายการที่ขาด
- `alert_expiring`, `alert_low_stock`: ใช้แสดงการแจ้งเตือน (มี 2 กลุ่ม)

## 4. ฟังก์ชัน SQL (ทางเข้าเดียวสำหรับแก้ยอดของคงเหลือ)

| ฟังก์ชัน | ทำอะไร |
|---|---|
| `check_in(items jsonb)` | รับแถวที่ซื้อ แปลงหน่วย คิดต้นทุนต่อหน่วยฐาน = ราคารวม ÷ ปริมาณฐาน สร้างรอบที่ซื้อ + movement `purchase` ปิดรายการ shopping ใน transaction เดียว |
| `add_opening_stock(...)` | สร้างรอบที่ซื้อสำหรับยอดคงเหลือเริ่มต้น (movement `opening`) |
| `record_cooking(menu_id, qty, note)` | คำนวณปริมาณที่ต้องตัดต่อวัตถุดิบ = Σ(สูตร qty × จำนวนจาน ÷ yield) ล็อกรอบที่ซื้อที่ไม่หมดอายุเรียงตาม `expires_on` (null ไว้ท้ายสุด) ตัดตามลำดับ ข้ามหลายรอบได้ บันทึก movement `cook` ต่อรอบ คำนวณ `total_cost` สร้างแถว `cooking_logs` สถานะ `done` ถ้าของไม่พอ **ไม่ตัดเลย** และส่งรายการที่ขาดกลับ |
| `cancel_cooking(cooking_log_id)` | ถ้าสถานะ `done` สร้าง movement `cook_reversal` คืนยอดเข้ารอบที่ซื้อเดิมตาม movement ของบันทึกนั้น แล้วเปลี่ยนสถานะเป็น `cancelled` (ยกเลิกซ้ำไม่ได้) |
| `adjust_stock(...)` | ปรับยอดจากการนับ (เพิ่ม = สร้างรอบที่ซื้อใหม่ ต้นทุนเริ่มต้นเท่าเฉลี่ย, ลด = ตัดตามลำดับเดียวกัน) |
| `discard_lot(lot_id)` | ตัดรอบที่หมดอายุทิ้ง บันทึกเป็น `waste` |

ทุกฟังก์ชันเช็กว่าแถวเป็นของ `auth.uid()` และรันด้วยสิทธิ์ของผู้เรียก (ไม่ข้าม RLS ยกเว้นจำเป็นจริง) และส่งรหัสข้อผิดพลาดที่คงที่ (เช่น `INSUFFICIENT_STOCK`) ให้หน้าเว็บแปลงเป็นข้อความไทย

## 5. ความปลอดภัยและการเข้าถึง

- **Auth:** Supabase Auth ด้วย Email/Password **ปิดการสมัครสมาชิกใหม่** หลังสร้างบัญชีเจ้าของร้านแล้ว
- **RLS เปิดทุกตาราง:** นโยบาย `owner_id = auth.uid()` สำหรับ select/insert/update; `stock_movements` ห้าม update/delete
- **การเขียนยอดทำผ่านฟังก์ชันเท่านั้น:** ถอดสิทธิ์ insert/update ตรงบน `lots` และ `stock_movements` จาก role ของผู้ใช้ (ให้ผ่านฟังก์ชันที่ตรวจสิทธิ์แล้ว)
- ใช้เฉพาะ anon key ฝั่งหน้าเว็บ **ไม่นำ service role key ไปไว้ในโค้ดหน้าเว็บ** เก็บความลับใน environment variables ของ Vercel และไฟล์ `.env.local` (ไม่ commit)

## 6. หน้าจอและการไหลของข้อมูล

ชื่อในคอลัมน์แรกคือชื่อที่แสดงบนหน้าจอ (ภาษาไทยล้วน ตามภาคผนวก ก. ของเอกสารออกแบบหลัก)

| ชื่อหน้า | เนื้อหา | อุปกรณ์หลัก |
|---|---|---|
| หน้าหลัก | การแจ้งเตือน 2 กลุ่ม (ใกล้หมดอายุ, ของใกล้หมด), ประวัติทำอาหารล่าสุด | มือถือ+คอม |
| คลังวัตถุดิบ | รายการวัตถุดิบ แยกตามช่องเก็บ, ขยายดูรอบที่ซื้อ, ปรับยอดตามการนับ/ตัดทิ้ง/เพิ่มยอดคงเหลือเริ่มต้น | คอม |
| วัตถุดิบ | จัดการวัตถุดิบ หน่วยซื้อ จุดสั่งซื้อซ้ำ | คอม |
| รายการอาหารและสูตร | ฟอร์มหน้าเดียวสร้างรายการอาหาร+สูตร, อัตราที่ใช้ได้จริง, ดูจำนวนที่ทำได้และต้นทุนประมาณ, ปุ่มบันทึกการทำ, ปุ่มเพิ่มของที่ขาดเข้ารายการซื้อของ | คอม |
| ประวัติทำอาหาร | ประวัติการทำ (ทำอะไร กี่จาน เมื่อไร ต้นทุน), บันทึกการทำ, ยกเลิก (ชื่อหน้าผู้ใช้ยืนยันแล้ว) | มือถือ+คอม |
| รายการซื้อของ | วางแผนซื้อ (เตือนซื้อซ้ำ) และจ่ายตลาด → นำเข้าคลัง | **มือถือ** |

**ตัวอย่างการไหล "บันทึกการทำ":** เลือกรายการอาหาร ใส่จำนวนจานและหมายเหตุ กดบันทึก → หน้าเว็บเรียก `record_cooking` → ฐานข้อมูลล็อกรอบที่ซื้อ ตัดตามหลักใช้ของที่หมดอายุก่อน บันทึก movement คิดต้นทุน → ส่งผลกลับ (สำเร็จ หรือรายการที่ขาด) → หน้าเว็บรีเฟรชข้อมูล

**ฉบับร่างรายการซื้อของ:** เก็บใน `localStorage` ของเบราว์เซอร์ ทุกครั้งที่ติ๊กหรือกรอกราคา ล้างเมื่อนำเข้าคลังสำเร็จ ไม่ใช่ออฟไลน์เต็มรูปแบบ (ไม่ใช้ service worker ในเวอร์ชันแรก)

**ข้อกำหนดภาษา:** ผู้ใช้กำหนดให้ทุกอย่างที่เห็นเป็นภาษาไทยล้วน ทำให้มีผลต่อการสร้างดังนี้
- เก็บข้อความหน้าจอทั้งหมดในไฟล์ศัพท์กลางไฟล์เดียว (เช่น `src/lib/th.ts`) ไม่เขียนข้อความกระจายในคอมโพเนนต์ เพื่อให้ตรวจได้ว่าไม่มีอังกฤษหลงเหลือ
- ฟังก์ชัน SQL ต้องส่งรหัสข้อผิดพลาดที่คงที่ หน้าเว็บแปลงเป็นข้อความไทยจากไฟล์ศัพท์ ห้ามแสดงข้อความดิบของฐานข้อมูล
- ตั้ง `<html lang="th">` และชื่อแท็บเบราว์เซอร์เป็นไทย (ส่วนชื่อแอปคือ Inven2Food) ใช้ฟอนต์ที่รองรับภาษาไทยดี
- เพิ่มการทดสอบ Playwright ที่สแกนข้อความที่มองเห็นในทุกหน้า แล้วล้มถ้าพบตัวอักษรละติน (ยกเว้นชื่อแอป Inven2Food, คำว่า Email และ Password บนหน้าเข้าสู่ระบบ และข้อมูลที่ผู้ใช้พิมพ์เอง)
- คำทับศัพท์ที่เขียนด้วยอักษรไทยก็ไม่ใช้ ตามภาคผนวก ก. (เช่น "รอบที่ซื้อ" แทน "ล็อต")
- ชื่อในโค้ดที่ผู้ใช้ไม่เห็น (ตาราง ฟังก์ชัน SQL ตัวแปร ไฟล์) เป็นภาษาอังกฤษ ผู้ใช้ยืนยันแล้ว

```
│  ├─ app/                        หน้าต่าง ๆ (Next.js App Router)
│  ├─ components/                 UI ที่ใช้ร่วมกัน
│  ├─ lib/                        supabase client, th.ts, ฟังก์ชันช่วย (วันที่ พ.ศ., ฟอร์แมตเงิน)
│  └─ types/                      ชนิดข้อมูลที่ generate จากสคีมา

```

## 8. ลำดับการสร้าง (ข้อเสนอ)

1. ตั้งโปรเจกต์ Next.js + Supabase, auth, RLS พื้นฐาน, ไฟล์ศัพท์ไทย, deploy ว่าง ๆ ขึ้น Vercel
2. วัตถุดิบ + หน่วยซื้อ + รอบที่ซื้อ + ยอดคงเหลือเริ่มต้น + คลังวัตถุดิบ (พร้อมการทดสอบ movement = ยอดรอบที่ซื้อ)
3. รายการอาหารและสูตร + view จำนวนที่ทำได้
4. บันทึกการทำ + `record_cooking` / `cancel_cooking` (ตัดตามหลักใช้ของที่หมดอายุก่อน, yield, ต้นทุน) — **ส่วนที่เสี่ยงที่สุด ทดสอบหนักที่สุด**
5. รายการซื้อของ + นำเข้าคลัง + ฉบับร่าง
6. การแจ้งเตือน + หน้าหลัก

หลังข้อ 4 ใช้งานหลักได้แล้ว (ทำอาหารแล้วตัดของ) ข้อ 5–6 เติมต่อได้

## 9. การทดสอบ (สิ่งที่ต้องมีอย่างน้อย)

- ตัดของ: ข้าม 2–3 รอบที่ซื้อ, รอบที่หมดอายุถูกข้าม, รอบไม่มีวันหมดอายุไว้ท้ายสุด, ของไม่พอแล้วไม่ตัดเลย
- อัตราที่ใช้ได้จริง: 85% ตัดมากขึ้น 1/0.85 เท่า และต้นทุนรวมส่วนที่เสีย
- การแปลงหน่วยตอนนำเข้าคลังและต้นทุนต่อหน่วยฐาน (ไม่ปัดเศษ)
- ยกเลิกการทำ คืนยอดเข้ารอบที่ซื้อเดิม แม้รอบหมดอายุแล้ว และยกเลิกซ้ำไม่ได้
- ความคงที่: `lots.qty_remaining` = ผลรวม `qty_delta` ของรอบนั้นเสมอ
- RLS: ผู้ใช้อื่นอ่าน/เขียนข้อมูลไม่ได้
- Playwright: เส้นทาง "บันทึกการทำ → ของคงเหลือลด" และ "จ่ายตลาด → นำเข้าคลัง → รอบที่ซื้อใหม่ในคลังวัตถุดิบ" และการสแกนภาษาในทุกหน้า

## 10. ความเสี่ยงและสิ่งที่ต้องระวัง

- **ผู้ใช้กรอกข้อมูลมากตอนเริ่ม** (วัตถุดิบ หน่วยซื้อ สูตร ยอดคงเหลือเริ่มต้น): ถ้าหนักเกินไปจะเลิกใช้ ควรทำฟอร์มเพิ่มต่อเนื่องที่เร็ว และอาจเพิ่มการนำเข้า CSV ภายหลังถ้าจำเป็น
- **ตัวเลขไม่ตรงของจริง:** ต้องมีการนับและปรับยอดที่ใช้ง่าย ทุกการปรับต้องเห็นประวัติ
- **ต้องมีอินเทอร์เน็ต:** ที่ตลาดสัญญาณไม่ดีอาจกรอกไม่ทัน ฉบับร่างใน `localStorage` ช่วยเรื่องข้อมูลไม่หาย แต่นำเข้าคลังต้องใช้เน็ต
- **ผูกกับ Supabase:** ฟังก์ชัน SQL และ RLS เป็น Postgres มาตรฐาน ย้ายไป Postgres ที่อื่นได้ถ้าจำเป็น ส่วน Auth จะต้องเปลี่ยน
- **โซนเวลา:** ใช้ Asia/Bangkok ตัดสินว่า "หมดอายุหรือยัง" ไม่ใช่ UTC
